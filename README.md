# PR Flow

ระบบ Purchase Request Management สำหรับองค์กร พร้อม workflow อนุมัติ, dashboard, notifications และรายงานส่งออก

## Tech Stack

- Next.js 15 App Router
- TypeScript
- Tailwind CSS
- shadcn/ui
- Prisma ORM
- PostgreSQL
- Zod

## ฟีเจอร์หลัก

- Login / Logout ด้วย JWT cookie รองรับ `email`, `username` และ `phone`
- Role Based Access Control: `Employee`, `Approver`, `Purchasing`, `Admin`
- Dashboard สรุป PR รออนุมัติ, อนุมัติแล้ว, ถูกปฏิเสธ และมูลค่ารวม
- สร้าง/แก้ไข Purchase Request พร้อมคำนวณยอดรวมอัตโนมัติ
- Approval Workflow: Draft, Pending Approval, Approved, Rejected, Ordered, Completed
- รับสินค้าแยกรายการได้หลายรอบ รองรับรับเกินพร้อมเหตุผล และปิดยอดค้างรับที่ไม่รับต่อ
- Notification Bell สำหรับเหตุการณ์สำคัญ
- Reports แยกตามเดือน, แผนก และผู้ขอซื้อ
- Export Excel และ PDF
- รองรับภาษาไทย, Dark Mode และ responsive ทุกหน้าจอ

## เริ่มต้นใช้งาน

1. ติดตั้ง dependencies

```bash
npm install
```

2. เตรียม environment

```bash
cp .env.dev.example .env.dev
```

ไฟล์ env จริงถูก ignore จาก Git ทั้งหมด ให้เก็บ secret ในไฟล์เหล่านี้เท่านั้น:

```bash
.env.dev
.env.uat
.env.prod
```

ไฟล์ template ที่ commit ได้คือ:

```bash
.env.dev.example
.env.uat.example
.env.prod.example
.env.example
```

3. เปิด PostgreSQL ด้วย Docker

```bash
docker compose up -d postgres
```

หมายเหตุ: โปรเจ็กนี้ map database ออกที่ `localhost:5433` เพื่อหลบพอร์ต `5432` ที่มักถูกใช้งานอยู่แล้ว

4. apply migration และ seed data

```bash
npm run db:migrate:dev
npm run db:seed:dev
```

5. เปิด dev server

```bash
npm run dev
```

จากนั้นเปิด `http://localhost:3000`

## Environment Files

โปรเจ็กต์นี้แยก env เป็น 3 ชุด:

- `dev`: ใช้ `.env.dev` และ optional override `.env.dev.local`
- `uat`: ใช้ `.env.uat` และ optional override `.env.uat.local`
- `prod`: ใช้ `.env.prod` และ optional override `.env.prod.local`

ลำดับการโหลดของ helper script คือ `.env` -> `.env.<env>` -> `.env.<env>.local` โดยค่า environment ที่มาจาก shell, GitHub Actions หรือ Vercel จะชนะไฟล์ local เสมอ

ตัวอย่างการใช้งาน:

```bash
npm run dev
npm run build:uat
npm run db:deploy:prod
```

## CI/CD และ Deployment

โปรเจ็กต์นี้เตรียม GitHub Actions ไว้ 2 workflow:

- `CI`: รันเมื่อเปิด PR, push เข้า `main` หรือกด manual โดยจะติดตั้ง dependencies, เปิด PostgreSQL service, รัน `typecheck`, `lint`, `build` และ E2E tests
- `Deploy to Vercel`: รัน production deploy อัตโนมัติหลัง `CI` บน `main` ผ่าน หรือกด manual ได้จาก GitHub Actions

ต้องตั้งค่า GitHub repository secrets เหล่านี้ก่อน deploy:

```bash
VERCEL_TOKEN=...
VERCEL_ORG_ID=...
VERCEL_PROJECT_ID=...
DATABASE_URL=...
```

และต้องตั้งค่า Environment Variables ใน Vercel สำหรับ runtime:

```bash
DATABASE_URL=...
JWT_SECRET=...
APP_URL=https://your-production-domain
EMAIL_PROVIDER=google_apps_script
GOOGLE_MAIL_WEBHOOK_URL=https://script.google.com/macros/s/YOUR_DEPLOYMENT_ID/exec
GOOGLE_MAIL_WEBHOOK_SECRET=replace-with-a-long-random-secret
EMAIL_FROM_NAME="PR Flow"
```

ถ้าตั้งค่า `EMAIL_PROVIDER`, `GOOGLE_MAIL_WEBHOOK_URL`, `GOOGLE_MAIL_WEBHOOK_SECRET` และ `EMAIL_FROM_NAME` ระบบจะส่งอีเมลตาม notification ผ่าน Google Apps Script HTTPS gateway ให้อัตโนมัติ หากยังตั้งค่าไม่ครบ ระบบจะสร้าง notification ในแอปตามเดิมโดยกำหนดสถานะอีเมลเป็น `DISABLED`

ขั้นตอน deploy production ใน workflow คือ:

1. `vercel pull --environment=production`
2. `npm run db:deploy` เพื่อ apply Prisma migrations กับ production database
3. `vercel build --prod`
4. `vercel deploy --prebuilt --prod`

หมายเหตุ: ไฟล์แนบปัจจุบันบันทึกลง filesystem local ในโฟลเดอร์ `storage/` ถ้าจะใช้งาน production บน serverless platform ควรเปลี่ยนเป็น persistent object storage ก่อนใช้งานไฟล์แนบจริงจัง

## แชร์ลิงก์ PR

- เปิดหน้ารายละเอียด PR แล้วกด **แชร์ PR** เพื่อคัดลอกลิงก์ส่งให้ฝ่ายจัดซื้อหรือผู้อนุมัติ หรือเลือกแชร์ผ่านแอปบนอุปกรณ์เมื่อเบราว์เซอร์รองรับ
- หากเบราว์เซอร์ไม่อนุญาตให้คัดลอกอัตโนมัติ สามารถเลือกข้อความในช่องลิงก์และคัดลอกเองได้
- ผู้รับต้องล็อกอินด้วยบัญชีที่มีสิทธิ์ดู PR ใบนั้น หากยังไม่ล็อกอิน ระบบจะกลับมาที่ PR เดิมหลังเข้าสู่ระบบสำเร็จ ลิงก์ไม่เพิ่มสิทธิ์และไม่มี token สำหรับข้ามการล็อกอิน

## การรับสินค้าหลายรอบและปิดยอดค้างรับ

ก่อนใช้ฟีเจอร์นี้ ให้รัน migration ล่าสุดด้วย `npm run db:deploy` ใน environment ที่ต้องการอัปเดต ข้อมูลที่ยืนยันรับของในระบบเดิมจะถูกนำเข้าเป็นประวัติรับเต็มจำนวนหนึ่งรอบ โดยคงวันที่และเลขเอกสารเดิมไว้

- หลังเปิด PO ผู้ที่มีสิทธิ์ดู PR สามารถบันทึกวันที่และจำนวนรับจริงแยกรายการในแต่ละรอบได้ จำนวนรับต้องเป็นจำนวนเต็มมากกว่า 0
- แต่ละรายการแสดงจำนวนสั่งเดิม จำนวนรับสะสม จำนวนปิดยอดค้างรับ ยอดค้างรับ และยอดรับเกิน โดยยอดค้างรับไม่ติดลบ และการรับจริงไม่แก้จำนวนสั่งเดิม
- หากรับสะสมเกินจำนวนสั่ง ต้องระบุเหตุผลรับเกิน สามารถบันทึกยอดเกินหลังรับครบได้จนกว่าจะปิด PR
- เมื่อรับสินค้าแล้วบางส่วน ฝ่ายจัดซื้อหรือแอดมินสามารถปิดยอดที่ไม่รับต่อได้ พร้อมระบุจำนวนและเหตุผล จำนวนที่ปิดต้องไม่เกินยอดค้างรับ และรับเพิ่มเกินยอดค้างรับของรายการที่ปิดบางส่วนแล้วไม่ได้
- ระบบเก็บประวัติแต่ละรอบพร้อมผู้บันทึก วันที่ จำนวน เหตุผล และเลขเอกสาร สามารถบันทึกเลขรับของหรือเลขใบกำกับภาษีแยกแต่ละรอบได้
- ปิด PR ได้เมื่อทุกรายการไม่มียอดค้างรับ และทุกรอบที่รับสินค้ามีเลขรับของหรือเลขใบกำกับภาษีอย่างน้อยหนึ่งรายการ รายการปิดยอดค้างรับไม่ต้องมีเอกสารรับของ
- เมื่อมีการรับสินค้าแล้ว แม้ยังรับไม่ครบ จะยกเลิก PR ทั้งใบไม่ได้ ให้ปิดเฉพาะยอดที่ไม่รับต่อเพื่อคงประวัติสินค้าที่รับจริง
- การบันทึกแต่ละครั้งตรวจเวอร์ชันข้อมูล หากมีคนอื่นบันทึกก่อน ระบบจะให้โหลดข้อมูลใหม่เพื่อป้องกันยอดรับซ้ำ

ตัวอย่าง: สั่ง 100 ชิ้น → รับ 40 ชิ้น → รับอีก 30 ชิ้น → ปิดส่วนที่ไม่รับต่อ 30 ชิ้น ผลลัพธ์คือรับจริง 70 ชิ้น ปิดยอดค้างรับ 30 ชิ้น และยอดค้างรับ 0 ชิ้น

ชุดทดสอบรับสินค้าแบ่งตามพฤติกรรมที่ต้องตรวจ โดยใช้ฐานข้อมูลทดสอบที่ชื่อลงท้าย `_e2e` เท่านั้น:

| ไฟล์ใน `tests/e2e/` | ขอบเขตที่ตรวจ |
| --- | --- |
| `purchase-request-receipts.spec.ts` | รับหลายรอบ รับเกิน ปิดยอดค้าง เอกสารแต่ละรอบ และ workflow ผ่านหน้าจอ |
| `purchase-request-receipt-access.spec.ts` | สิทธิ์ผู้ใช้ การเข้าถึง PR ของผู้อื่น สถานะก่อนรับ/หลังปิดงาน และ API เดิม |
| `purchase-request-receipt-validation.spec.ts` | หลายรายการต้องสำเร็จหรือถูกปฏิเสธทั้งชุด ขอบเขตจำนวน/เหตุผล วันที่ และยอดที่ปิดบางส่วน |
| `purchase-request-receipt-concurrency.spec.ts` | บันทึกรับแข่งกับปิดยอด ยกเลิก PO ปิด PR และแก้เลขเอกสาร รวมถึงการส่งคำสั่งเดิมซ้ำ |
| `purchase-request-receipt-ui.spec.ts` | ตัวกรอง คิว dashboard สิทธิ์บนหน้าจอ ประวัติหลัง reload ภาษาไทย/อังกฤษ และการกู้คืนฟอร์มเมื่อข้อมูลเปลี่ยน |

รันทั้งโครงการด้วย `npm run test:e2e` หรือรันเฉพาะส่วนรับสินค้าด้วย `npm run test:e2e -- purchase-request-receipt` การทดสอบ API ใช้การล็อกอินผ่าน API เพื่อเตรียม session ส่วนกรณี UI ใช้ browser ทดสอบปุ่ม ฟอร์ม การแจ้งเตือน และการแสดงผลจริง ชุด authentication เดิมยังทดสอบการล็อกอินผ่านหน้าจอแยกต่างหาก

## แปลง PR เป็นใบสั่งซื้อ (PO)

หลังรัน migration ล่าสุดด้วย `npm run db:deploy` ฝ่ายจัดซื้อหรือแอดมินสามารถเปิด PR ที่อนุมัติแล้วและเลือก **แปลง PR เป็น PO** ได้

- ระบุผู้ขายของสินค้าแต่ละรายการ ระบบรวมรายการของผู้ขายเดียวกันเป็น PO ใบเดียว และออกหลาย PO เมื่อมีหลายผู้ขาย โดยสามารถปรับผู้ขายจากข้อมูลแนะนำใน PR ได้
- กรอกที่อยู่และข้อมูลติดต่อผู้ขาย สถานที่ส่งสินค้า เงื่อนไขชำระเงิน วันที่คาดว่าจะส่ง และหมายเหตุแยกแต่ละผู้ขายได้
- ก่อนกดสร้าง PO ฝ่ายจัดซื้อและแอดมินสามารถเพิ่มหรือลบสินค้า แก้ไขชื่อ รายละเอียด จำนวน หน่วย และราคาต่อหน่วยได้ โดยต้องมีสินค้าอย่างน้อย 1 รายการและไม่เกิน 500 รายการ ยอดรวมจะคำนวณใหม่ทันที
- เลือกเฉพาะรายการที่จะซื้อได้ด้วยช่องทำเครื่องหมาย รายการที่ไม่เลือกจะยังอยู่ใน PR เพื่อเปิด PO ครั้งถัดไป ส่วนปุ่ม **ลบรายการสินค้า** จะลบรายการรอซื้อออกจาก PR เมื่อสร้าง PO สำเร็จ
- กด **ดู Preview PO** เพื่อตรวจเอกสาร A4 ของผู้ขายทุกใบ รวมข้อมูลบริษัท ผู้รับสินค้า ราคา ส่วนลด และ VAT เอกสารแสดงเครื่องหมายร่างทุกหน้า โดยขั้นตอนนี้ยังไม่แก้ PR ไม่ออกเลข PO และไม่เพิ่มประวัติหรือแจ้งเตือน
- กด **กลับไปแก้ไข** เพื่อกลับไปปรับข้อมูลเดิม หรือ **ยืนยันสร้าง PO** เพื่อบันทึกตามข้อมูลที่ตรวจแล้ว หากข้อมูลบริษัท ผู้ขาย หรือข้อมูลที่มีผลกับเอกสารเปลี่ยนระหว่าง Preview และยืนยัน ระบบจะให้ดู Preview ใหม่ก่อนบันทึก
- เมื่อสร้าง ระบบปรับรายการและยอดรวมใน PR ให้ตรงกับข้อมูลจัดซื้อ พร้อมเก็บเลข PO และรายละเอียดก่อน/หลังการเพิ่ม ลบ หรือแก้ไขไว้ใน Timeline ขั้นตอน **ปรับรายการก่อนออก PO** รายการที่เลือกต้องไม่ซ้ำกับ PO ที่ยังมีผล
- ระบบตรวจเวอร์ชัน PR ก่อนบันทึก หากมีการแก้ไขหรือเปลี่ยนสถานะระหว่างเปิดหน้า ต้องโหลดข้อมูลล่าสุดก่อน การปรับรายการและการสร้าง PO สำเร็จพร้อมกันภายในธุรกรรมเดียว
- เมื่อสร้างสำเร็จ ระบบออกเลข PO แยกแต่ละใบและเปลี่ยน PR ที่มีการสั่งซื้อเป็น **สั่งซื้อแล้ว** ภายในธุรกรรมเดียวกัน สามารถเปิด PO เพิ่มจากรายการที่เหลือได้ โดยระบบป้องกันการสั่งรายการเดียวกันซ้ำจากการส่งซ้ำหรือบันทึกพร้อมกัน
- หน้ารายละเอียด PR แสดง PO ที่เกี่ยวข้อง การเปิด PO รวมหลาย PR และ PDF ต้องมีสิทธิ์ดู PR ต้นทางครบทุกใบ ผู้ที่ดูได้เฉพาะ PR ของตนยังเห็นเฉพาะข้อมูลส่วนของตนในหน้า PR
- การรับสินค้าและปิดยอดค้างรับยังบันทึกผ่านหน้า PR โดยใช้เฉพาะแถว PO ที่มาจาก PR ใบนั้น และไม่นับ PO ที่ยกเลิก การรับครบเพียง PO แรกไม่ทำให้ PR ที่ยังมีรายการรอเปิด PO ปิดงานอัตโนมัติ จำนวนสั่งและมูลค่าใน PO เปลี่ยนได้ผ่านการแก้ไขที่ได้รับอนุมัติเท่านั้น
- ปุ่ม **อนุมัติเปิด PO** เดิมยังใช้ยืนยันการสั่งซื้อที่จัดทำในระบบภายนอกได้ การยืนยันแบบเดิมเปลี่ยนสถานะ PR โดยไม่สร้างเอกสาร PO ภายในย้อนหลัง

ชุดทดสอบ `tests/e2e/purchase-orders.spec.ts` ตรวจการแยกผู้ขายและยอดรวม สิทธิ์เข้าถึง ข้อมูลต้นทาง รายการขาด/ซ้ำ/ต่าง PR การบันทึกพร้อมกัน การยกเลิก การรับสินค้า และการสร้าง/พิมพ์ PO ผ่านหน้าจอ รันเฉพาะส่วนนี้ด้วย `npm run test:e2e -- purchase-orders.spec.ts` โดยใช้ฐานข้อมูลทดสอบที่ชื่อลงท้าย `_e2e` เท่านั้น

ทดสอบ Preview ก่อนสร้างด้วย `npm run test:e2e -- purchase-order-creation-preview.spec.ts` ครอบคลุมการไม่เขียนข้อมูลก่อนยืนยัน การกลับไปแก้ไข การยืนยันเพียงครั้งเดียว และการตรวจข้อมูลเปลี่ยนระหว่าง Preview กับบันทึก โดยใช้ฐานข้อมูลทดสอบแยกเช่นกัน

## รวมหลาย PR และยกเลิกเฉพาะ PO

- ฝ่ายจัดซื้อและแอดมินเปิดเมนู **สร้าง PO รวม PR** (`/purchase-orders/new`) ค้นหาและเลือก PR ที่อนุมัติแล้วหรือสั่งซื้อไปบางส่วน จากนั้นเลือกรายการที่ยังไม่ได้เปิด PO รายการจากหลาย PR ที่เลือกผู้ขายทะเบียนเดียวกัน หรือพิมพ์ชื่อเดียวกัน จะรวมใน PO ใบเดียว
- เลือกซื้อเป็นรายแถว โดยยังแก้จำนวนและราคาได้ตามกติกาเดิม ยังไม่รองรับการแบ่งจำนวนสินค้าแถวเดียวไปเปิดหลาย PO พร้อมกัน แถวที่เพิ่มใหม่ต้องระบุ PR ต้นทาง
- ตัวอย่าง: PR-A มี 10 รายการ เลือกซื้อ 3 รายการร่วมกับ PR-B อีก 2 รายการ จะได้ PO รวม 5 รายการ และ PR-A ยังเหลือ 7 รายการรอเปิด PO
- PO/PDF แสดง PR ต้นทางหลายใบและเลข PR ของสินค้าแต่ละแถว ส่วนลดท้าย PO กระจายกลับแต่ละ PR ตามแถวสินค้า จึงไม่บวกยอดทั้ง PO ซ้ำในทุก PR
- การแก้ไข PO ที่รวม PR ซึ่งมีผู้อนุมัติต่างกัน ต้องให้แอดมินหรือฝ่ายบริหาร/จัดการอนุมัติทั้งใบ และผู้อนุมัติต้องไม่ใช่ผู้เสนอแก้ไข ถ้าผู้อนุมัติเดิมเป็นคนเดียวกันยังใช้กติกาสิทธิ์เดิม รายการและยอดเงินจริงเปลี่ยนเมื่ออนุมัติแล้ว พร้อม Timeline ของ PR ที่ได้รับผล
- ปุ่ม **ยกเลิกเฉพาะ PO** ใช้ได้สำหรับฝ่ายจัดซื้อหรือแอดมิน เมื่อ PO ยังไม่เคยรับของหรือปิดยอด และไม่มีคำขอแก้ไขค้างอยู่ ต้องกรอกเหตุผล ระบบเก็บเอกสาร ผู้ยกเลิก เวลา และประวัติไว้ รายการกลับไปรอเปิด PO ใหม่โดยไม่ยกเลิก PR
- หลังยกเลิก PO ภายใน ให้เปิด PO ใหม่จากรายการที่กลับมารอซื้อ หากต้องเปลี่ยนข้อมูลผ่านผู้ขอซื้อ จัดซื้อส่ง PR กลับให้แก้ไขได้ โดยเอกสาร PO ที่ยกเลิกยังเก็บรายการเดิมไว้ การยืนยันสั่งซื้อภายนอกใช้กับ PR ที่ยังไม่มีประวัติ PO ภายในเท่านั้น
- Migration `202610301000_multi_pr_orders` เพิ่มความสัมพันธ์หลาย PR สถานะ PO และ PR ต้นทางต่อแถว โดยย้ายข้อมูลเอกสารเดิมให้ใช้โครงสร้างใหม่ ก่อนใช้งานให้รัน `npm run db:deploy` ในสภาพแวดล้อมเป้าหมาย

ทดสอบด้วย `npm run test:e2e -- purchase-order-multi-pr` ครอบคลุมการทยอยเปิด รวมหลาย PR ส่วนลด/VAT สิทธิ์ การแก้ไขและอนุมัติ การยกเลิกและเปิดใหม่ การรับของแยกต้นทาง และหน้าจอบนมือถือ โดยใช้ฐานข้อมูลทดสอบแยกที่ชื่อลงท้าย `_e2e` เท่านั้น

ทดสอบการเพิ่ม/ลบ/แก้ไขสินค้าก่อนออก PO รวมถึงยอดเงิน ประวัติ การปรับ PR ให้ตรงกับ PO การรับสินค้าตาม PO และการบันทึกพร้อมกันด้วย `npm run test:e2e -- purchase-order-preparation.spec.ts` โดยใช้ฐานข้อมูลทดสอบแยกที่รัน migration ล่าสุดแล้ว

## เอกสาร PO และ PDF

เปิด PO แล้วกด **พิมพ์** หรือ **ดาวน์โหลด PDF** เอกสารเป็น A4 แนวตั้ง ฟอนต์ Noto Sans Thai พร้อมเลขหน้าและหัวตารางซ้ำ ใช้แผนจัดวางชุดเดียวกันสำหรับหน้าดู หน้าพิมพ์ และไฟล์ PDF การดาวน์โหลดตรวจสิทธิ์ด้วยกติกาเดียวกับการเปิด PO และไม่เก็บ PDF ไว้ใน public storage

- ข้อมูลผู้ขาย ที่อยู่ส่งสินค้า เงื่อนไขชำระเงิน หมายเหตุ และรายการ ใช้สำเนาที่บันทึกกับ PO ฉบับปัจจุบัน ไม่ใช้คำขอแก้ไขที่ยังรออนุมัติ และไม่ดึงความเห็นภายในหรือเหตุผลอนุมัติจาก PR
- ใช้ราคา จำนวนเงินรายรายการ และยอดรวมที่บันทึกไว้ แสดงสกุลเงิน THB และแยกราคาก่อน VAT / VAT / ยอดสุทธิตามรูปแบบภาษีของ PO และแต่ละสินค้า ราคาที่รวม VAT แล้วจะไม่บวกภาษีซ้ำ ส่วน PO เดิมที่ยังไม่ระบุภาษียังคงยอดเดิมและแสดง VAT เป็น `-`
- ผู้รับสินค้าเลือกจากพนักงานที่เปิดใช้งานทุกแผนก ยกเว้นแอดมิน โดยเริ่มต้นจากผู้ขอซื้อใน PR ระบบเก็บชื่อและเบอร์โทรเป็นสำเนาใน PO ส่วนข้อมูลโลโก้ ใบเสนอราคา และค่าขนส่งยังไม่มีช่องเก็บข้อมูล จึงแสดง `-` ไม่แทนด้วย `0.00` หรือค่าจากเอกสารตัวอย่าง รายละเอียดบรรจุภัณฑ์แสดงจากรายละเอียดสินค้าที่มีอยู่ ส่วนรหัสสินค้าไม่มีฟิลด์แยก
- พิมพ์ชื่อผู้จัดทำที่ระบบบันทึกไว้ และเว้นพื้นที่ลายเซ็นกับวันที่ ไม่มีการนำผู้อนุมัติ PR มาอ้างว่าเซ็นอนุมัติ PO สถานะ PR ปกติไม่แสดงบนเอกสาร แต่คงคำเตือนยกเลิก/ขอยกเลิก/มีคำขอแก้ไขค้างตามระบบเดิม
- ชื่อผู้จัดทำและเลข PR มาจากความสัมพันธ์ข้อมูลปัจจุบัน ข้อมูลบริษัทผู้ซื้อใช้สำเนาขณะออก PO ส่วนหมายเหตุ PO ยังไม่มีการแยกประเภทภายใน/ภายนอก

ตรวจตัวจัดเอกสารโดยไม่แตะฐานข้อมูลด้วย `npm run test:po-document` ครอบคลุมเอกสารหน้าเดียว หลายหน้าพร้อมชื่อยาว ช่องว่าง/เงินจริงศูนย์/ยอดเงินที่ขาดหาย คำเตือน และจำนวนเงินตัวอักษร ส่วน `tests/e2e/purchase-orders.spec.ts` ตรวจการดาวน์โหลด PDF ผ่านเบราว์เซอร์ด้วย

## แชร์ PO ให้ซัพพลายเออร์

ฝ่ายจัดซื้อหรือแอดมินเปิด PO แล้วกด **แชร์** กรอก **อายุลิงก์ (วัน)** ได้ตั้งแต่ 1–365 วัน (ค่าเริ่มต้น 30 วัน) แล้วกด **สร้างลิงก์แชร์** จากนั้น **คัดลอกลิงก์** หรือ **แชร์ผ่านอุปกรณ์** เพื่อส่งต่อ ผู้รับเปิดดู พิมพ์ และดาวน์โหลด PDF ได้โดยไม่ต้องมีบัญชี หน้าจอแสดงวันหมดอายุของลิงก์ที่สร้างแล้ว

- เปิดหน้าต่างแชร์เป็นการอ่านข้อมูลลิงก์เดิม ไม่สร้างหรือยืดอายุลิงก์อัตโนมัติ หากต้องการเปลี่ยนอายุ ให้กรอกจำนวนวันแล้วกด **สร้างลิงก์ใหม่** ซึ่งจะเริ่มนับอายุใหม่และยกเลิกลิงก์เก่า ส่วน **ยกเลิกลิงก์แชร์** จะหยุดการเข้าถึงผ่านลิงก์นั้น
- หน้าสำหรับผู้ขายแสดงเฉพาะเอกสาร PO ฉบับที่ออกแล้ว ไม่มีลิงก์กลับ PR ประวัติภายใน หรือข้อมูลการแก้ไขที่ยังรออนุมัติ หมายเหตุที่กรอกใน PO เป็นส่วนหนึ่งของเอกสารให้ผู้ขายเห็น
- เมื่ออนุมัติแก้จำนวนหรือราคาของผู้ขายเดิม ลิงก์เดิมจะแสดงฉบับล่าสุด หากอนุมัติเปลี่ยนผู้ขาย ระบบยกเลิกลิงก์เดิมถาวร ต้องสร้างลิงก์สำหรับผู้ขายใหม่
- ลิงก์ใช้ไม่ได้เมื่อหมดอายุ ถูกยกเลิก PO ถูกยกเลิก หรือ PR ต้นทางใบใดใบหนึ่งถูกยกเลิก/กำลังขอยกเลิก ประวัติจัดการลิงก์เก็บใน Timeline โดยไม่บันทึก URL สำหรับเข้าถึง

ก่อนใช้งานรัน migration `202610301200_po_supplier_share` ด้วย `npm run db:deploy` ทดสอบด้วย `npm run test:e2e -- purchase-order-sharing.spec.ts` โดยใช้ฐานข้อมูลแยกที่ชื่อลงท้าย `_e2e` เท่านั้น

## ตรวจและเสนอแก้ไข PO

ก่อนใช้งาน ให้รัน migration ล่าสุดด้วย `npm run db:deploy` ฝ่ายจัดซื้อหรือแอดมินเปิด PR → ลิงก์ในส่วน **ใบสั่งซื้อ (PO)** → **แก้ไข PO** ได้ขณะ PR อยู่สถานะสั่งซื้อแล้วและยังมียอดค้างรับ

- แก้ผู้ขาย ข้อมูลติดต่อ ที่อยู่ส่งสินค้า เงื่อนไขชำระเงิน วันที่ส่ง หมายเหตุ และรายการสินค้า รวมถึงจำนวน ราคา การเพิ่มหรือลบรายการได้ตามเงื่อนไข ข้อมูลผู้ขายที่แก้ในขั้นตอนนี้มีผลเฉพาะ PO ไม่แก้ทะเบียนผู้ขาย
- รายการที่รับสินค้าหรือปิดยอดแล้วจะเปลี่ยนชื่อ รายละเอียด หน่วย ราคา หรือลบไม่ได้ และ PO ที่มีรายการดังกล่าวจะเปลี่ยนตัวผู้ขาย ชื่อผู้ขาย หรือเลขภาษีไม่ได้ จำนวนที่แก้ต้องไม่น้อยกว่ายอดรับรวมกับยอดปิดค้างรับ หากเคยรับเกิน สามารถคงจำนวนสั่งเดิมไว้ได้ แต่เมื่อเปลี่ยนจำนวนต้องครอบคลุมยอดที่รับและปิดแล้ว
- ระบุเหตุผลแล้วกด **ส่งแก้ไข PO เพื่ออนุมัติ** ทุกการแก้ไขจะรอพิจารณา โดยข้อมูล PO และ PR จริงยังคงเดิม ระหว่างมีคำขอค้างอยู่ ระบบพักการรับสินค้า การยกเลิก และการปิดงานของ PR ทั้งใบ
- ผู้อนุมัติ PR เดิม แอดมิน หรือฝ่ายบริหาร/จัดการที่มีสิทธิ์เปิด PO เพื่อตรวจข้อมูลก่อนและหลัง แล้วอนุมัติหรือไม่อนุมัติ โดยต้องไม่ใช่ผู้เสนอแก้ไข ผู้เสนอสามารถถอนคำขอของตนเองได้ การไม่อนุมัติหรือถอนคำขอต้องระบุเหตุผล
- เมื่ออนุมัติ ระบบปรับทั้ง PO และรายการ PR ที่เกี่ยวข้อง พร้อมยอดรวม โดยยอดค้างรับใช้รายการและจำนวนตาม PO เลข PO คงเดิมและฉบับแก้ไขเพิ่มขึ้นหนึ่งครั้ง ทั้ง Timeline ของ PR และหน้าประวัติ PO เก็บรายละเอียดก่อน/หลัง เหตุผล ผู้เสนอ และผลการพิจารณาให้ตรวจย้อนหลังได้
- Migration `202610241000_po_independent_items` ย้ายการติดตามยอดรับของ PO ไปเก็บในรายการ PO และเชื่อมประวัติรับของเดิมให้อัตโนมัติ การสั่งซื้อที่ไม่มี PO ภายในยังรับของตาม PR ได้ตามเดิม

ชุดทดสอบ `tests/e2e/purchase-order-changes.spec.ts` มี 28 กรณี ครอบคลุมการเสนอและพิจารณาแก้ไข สิทธิ์ ประวัติ ยอดรับ การบันทึกพร้อมกัน และ workflow ผ่านหน้าจอ รันด้วย `npm run test:e2e -- purchase-order-changes.spec.ts` โดยใช้ฐานข้อมูลทดสอบที่ชื่อลงท้าย `_e2e` เท่านั้น

## ราคาและ VAT ใน PO

- หน้าแก้ไข PO เริ่มจากรายการสินค้า จัดช่องจำนวน/ราคาไว้ในแถวเดียวกันบนจอใหญ่และเป็นการ์ดบนมือถือ เปิดคำอธิบาย ข้อมูลติดต่อ และการจัดส่งเพิ่มเติมได้ สรุปยอดเดิม ยอดใหม่ ส่วนต่าง เหตุผล และปุ่มส่งอนุมัติอยู่ด้านข้างบนจอใหญ่
- เลือกรูปแบบราคาทั้งใบได้ว่า **รวม VAT แล้ว**, **ยังไม่รวม VAT**, **ไม่มี VAT** หรือ **ยังไม่ระบุภาษี** และปรับแยกสินค้าได้ เลือก **ตามการตั้งค่าทั้งใบ** เพื่อให้สินค้านั้นใช้ค่ากลาง หรือใช้ปุ่ม **ใช้กับทุกรายการ** เพื่อล้างค่าที่ตั้งแยก
- กำหนดอัตรา VAT เป็นตัวเลข 0–100 ได้ไม่เกิน 2 ตำแหน่ง โดยค่าเริ่มต้นในแบบฟอร์มคือ 7% ทั้งหน้าสร้างและหน้าแก้ไขรองรับรูปแบบเดียวกัน
- ราคาที่กรอกและยอดสินค้า (`จำนวน × ราคา`) คงตามรูปแบบที่เลือก ระบบแยกยอดก่อน VAT และยอด VAT พร้อมคำนวณยอดสุทธิ โดยปัด VAT แบบ half-up เป็น 2 ตำแหน่งแยกรายการแล้วรวมยอด เอกสาร/PDF และหน้าประวัติใช้วิธีเดียวกัน
- เมื่อสร้าง PO หรืออนุมัติฉบับแก้ไข จะปรับรูปแบบราคา อัตรา และยอดสุทธิใน PR ให้ตรงกัน พร้อมเก็บก่อน/หลังใน Timeline การรับของยังใช้จำนวนและยอดรับสะสมจาก PO
- สินค้าที่รับหรือปิดยอดแล้วจะเปลี่ยนรูปแบบ VAT หรืออัตราที่มีผลกับสินค้านั้นไม่ได้ การแก้ข้อมูลอื่นยังต้องผ่านอนุมัติตามเดิม และการโหลด PO ใหม่หลังพบข้อมูลชนกันต้องกดยืนยันโหลดจากแบบฟอร์มเพื่อไม่ทิ้งฉบับร่างทันที
- Migration `202610241100_po_item_vat` เพิ่มข้อมูลภาษีโดยตั้ง PO เดิมเป็น **ยังไม่ระบุภาษี** ไม่คำนวณภาษีย้อนหลังหรือเปลี่ยนราคา ยอดรับ และคำขอแก้ไขที่มีอยู่

รันทดสอบเลขภาษีด้วย `npm run test:po-tax`, เอกสารด้วย `npm run test:po-document` และขั้นตอน VAT / แบบฟอร์มด้วย `npm run test:e2e -- purchase-order-vat.spec.ts purchase-order-edit-usability.spec.ts` บนฐานข้อมูลทดสอบแยกที่รัน migration ล่าสุดแล้ว

## ส่วนลดใน PO

- หน้าสร้างและแก้ไข PO ระบุส่วนลดรายสินค้าและทั้งใบได้ เลือก **จำนวนบาท** หรือ **เปอร์เซ็นต์** โดยส่วนลดบาทของสินค้าใช้กับยอดรวมรายการ (`จำนวน × ราคาต่อหน่วย`) ไม่ใช่ราคาต่อชิ้น
- หักส่วนลดรายสินค้าก่อน แล้วหักส่วนลดทั้งใบจากยอดคงเหลือ ส่วนลดทั้งใบกระจายตามสัดส่วนยอดคงเหลือและจัดสรรเศษสตางค์ตามลำดับรายการอย่างแน่นอน ยอดจัดสรรรวมจึงตรงกับส่วนลดที่กรอกทุกครั้ง
- ส่วนลดหักจากราคาที่กรอก: ถ้าเป็นราคารวม VAT จะหักจากยอดรวม VAT ก่อนแยกภาษีออก ถ้าเป็นราคาไม่รวม VAT จะหักก่อนคำนวณ VAT เพิ่ม จึงรองรับสินค้าที่เลือก VAT ต่างกันในใบเดียว
- สรุปยอดและ PDF แสดงราคาก่อนลด ส่วนลดรายสินค้า ส่วนลดทั้งใบ ยอดหลังลด ยอดก่อน VAT, VAT และยอดสุทธิ พร้อมแสดงรายละเอียดส่วนลดและยอดจัดสรรของแต่ละสินค้า ใช้การคำนวณเดียวกับหน้าจอและประวัติ
- ระบบไม่รับค่าติดลบ ทศนิยมเกิน 2 ตำแหน่ง เปอร์เซ็นต์เกิน 100 หรือส่วนลดเกินยอดคงเหลือ ลดครบ 100% ได้โดยยอดเงินเป็นศูนย์ แต่สินค้ายังต้องผ่านการรับของ/ปิดงานตามปกติ
- การแก้เฉพาะส่วนลดหรือรายละเอียดจะคงยอดตั้งต้นรายรายการที่เคยบันทึกไว้เมื่อจำนวนและราคาต่อหน่วยไม่เปลี่ยน เพื่อรองรับข้อมูลเก่า โดยหน้าจอและฝั่งบันทึกใช้ยอดตั้งต้นเดียวกัน
- การแก้ PO ที่ออกแล้วต้องส่งอนุมัติตามเดิม เมื่ออนุมัติจะปรับราคา/ส่วนลด/ยอดสุทธิใน PR และเก็บก่อน–หลังลง Timeline โดยคงยอดรับสะสมไว้ ส่วนลดทั้งใบหรือส่วนลดที่กระทบสินค้าซึ่งรับหรือปิดยอดแล้วจะเปลี่ยนไม่ได้ รวมถึงกรณีแก้สินค้าอื่นแล้วทำให้ยอดส่วนลดจัดสรรของสินค้าที่รับแล้วเปลี่ยน
- Migration `202610291000_po_discounts` ตั้งข้อมูลเดิมเป็นไม่มีส่วนลด (`NONE/0`) และยอดจัดสรรศูนย์ โดยไม่เปลี่ยนราคา ยอดรวม ประวัติรับของ หรือคำขอแก้ไขเดิม

ทดสอบสูตรส่วนลดและ VAT ด้วย `npm run test:po-tax`, เอกสารด้วย `npm run test:po-document` และขั้นตอนจริงด้วย `npm run test:e2e -- purchase-order-discounts.spec.ts purchase-order-discounts-ui.spec.ts` บนฐานข้อมูลทดสอบที่รัน migration ล่าสุดแล้ว แนวทางส่วนลดขณะขายและการคำนวณ VAT หลังหักส่วนลดดูได้จาก [คำสั่งกรมสรรพากร ป.86/2542](https://rd.go.th/3568.html)

## ทะเบียนผู้ขายและช่องทางติดต่อ

หลังรัน migration ล่าสุด ฝ่ายจัดซื้อและแอดมินสามารถเปิดเมนู **ทะเบียนผู้ขาย** เพื่อเพิ่มหรือแก้ไขข้อมูลผู้ขายได้ ระบบออกเลข `SUP-00001` ให้อัตโนมัติ พร้อมเก็บชื่อ เลขประจำตัวผู้เสียภาษี ที่อยู่ ผู้ติดต่อ เงื่อนไขชำระเงิน และหมายเหตุ

- เลือกช่องทางติดต่อได้ตั้งแต่ 1 ถึง 5 ช่องทาง ได้แก่ **LINE**, **โทรศัพท์**, **อีคอมเมิร์ซ**, **อีเมล** และ **อื่น ๆ** โดยเลือกหลายช่องทางพร้อมกันได้ แต่ละช่องทางต้องมีรายละเอียดและไม่ซ้ำกัน เช่น LINE ID เบอร์โทร หรือ URL ร้านค้า
- ค้นหาผู้ขายด้วยรหัส ชื่อ เลขภาษี ผู้ติดต่อ หรือรายละเอียดช่องทางติดต่อได้ พร้อมตัวกรองเปิดใช้งาน/ปิดใช้งาน และการแบ่งหน้า
- ปิดใช้งานผู้ขายที่ไม่ใช้แล้วแทนการลบ เพื่อคงประวัติเอกสารไว้ สามารถเปิดใช้งานอีกครั้งได้ และระบบตรวจเวอร์ชันขณะแก้ไขเพื่อป้องกันข้อมูลของผู้แก้ไขพร้อมกันทับกัน
- ตอนแปลง PR เป็น PO ใช้ช่องผู้ขายช่องเดียวเพื่อพิมพ์ค้นหาชื่อหรือรหัสแล้วเลือกผู้ขายจากทะเบียน หรือพิมพ์ชื่อผู้ขายใหม่ได้เลย หากเลือกจากทะเบียน ระบบเติมข้อมูลและช่องทางติดต่อทุกช่องทางให้โดยอัตโนมัติ ส่วนสถานที่ส่ง วันที่ส่ง และหมายเหตุของ PO ยังกรอกแยกได้ การพิมพ์ชื่อเองไม่เพิ่มทะเบียนผู้ขายอัตโนมัติ
- ระบบใช้ข้อมูลทะเบียนล่าสุดตอนออก PO และเก็บเป็นสำเนาในเอกสาร การแก้ไขหรือปิดใช้งานผู้ขายภายหลังไม่เปลี่ยนข้อมูลใน PO ที่ออกแล้ว ผู้ขายที่ปิดใช้งานไม่สามารถใช้สร้าง PO ใหม่ได้
- การสร้าง PO ด้วยข้อมูลผู้ขายที่กรอกเองยังใช้งานได้ และไม่สร้างทะเบียนผู้ขายขึ้นอัตโนมัติ

ชุดทดสอบ `tests/e2e/suppliers.spec.ts` ตรวจสิทธิ์ ทะเบียนหลายช่องทาง การค้นหา/แบ่งหน้า การแก้ไขพร้อมกัน การเปิด/ปิดใช้งาน ข้อมูลสำเนาใน PO การสร้าง PO จากทะเบียน และฟอร์มภาษาไทย/อังกฤษ รันเฉพาะส่วนนี้ด้วย `npm run test:e2e -- suppliers.spec.ts` โดยใช้ฐานข้อมูลทดสอบที่ชื่อลงท้าย `_e2e` เท่านั้น

## ข้อมูลบริษัทผู้ซื้อบน PO

หลังรัน migration `202610240900_add_company_profile` แอดมินเปิดเมนู **ข้อมูลบริษัท** (`/admin/company`) เพื่อบันทึกชื่อบริษัท ที่อยู่ เลขประจำตัวผู้เสียภาษี สาขา เบอร์โทร และอีเมลได้ ชื่อกับที่อยู่จำเป็นต้องกรอก เมนู หน้าแก้ไข และ API `/api/admin/company` จำกัดเฉพาะบทบาท `ADMIN`

- ข้อมูลที่บันทึกจะแสดงในหัวเอกสารผู้ซื้อบนหน้า PO เอกสารพิมพ์ และ PDF โดยใช้รูปแบบเอกสารชุดเดียวกัน
- การบันทึกจะเติมข้อมูลให้ PO เดิมที่ยังไม่มีข้อมูลบริษัท และ PO ใหม่จะเก็บข้อมูลบริษัทขณะออกเอกสาร การแก้ไขบริษัทภายหลังไม่เปลี่ยนข้อมูลใน PO ที่มีข้อมูลบริษัทแล้ว
- ฟอร์มตรวจเวอร์ชันก่อนบันทึก หากแอดมินอีกคนแก้ไขข้อมูลก่อน ระบบจะแจ้งให้โหลดข้อมูลล่าสุดแทนการบันทึกทับโดยไม่ทราบ

ก่อนนำโค้ดใหม่นี้ขึ้นใช้งาน ให้รัน migration ด้วยคำสั่ง deploy ของ environment ที่ใช้งาน เช่น `npm run db:deploy` (หรือ migration container ใน Docker) ไม่ต้องกรอกข้อมูลบริษัทผ่านไฟล์ environment

ตรวจเอกสารด้วย `npm run test:po-document` และทดสอบสิทธิ์ ฟอร์ม ข้อมูลบริษัทใน PO เดิม/ใหม่ เอกสารพิมพ์ และ PDF ด้วย `npm run test:e2e -- company-settings.spec.ts` โดยใช้ฐานข้อมูลทดสอบที่ชื่อลงท้าย `_e2e` เท่านั้น

## ปิดงานออเดอร์

ฝ่ายจัดซื้อและแอดมินจะเห็นปุ่ม **ปิดงาน** บนหน้ารายละเอียด PR และ PO ทันทีเมื่อ PR มีสถานะสั่งซื้อแล้ว โดยไม่จำกัดอายุออเดอร์ หากมี PO รอตรวจการแก้ไข ต้องพิจารณาการแก้ไขให้เสร็จก่อน

เมื่อยืนยัน ระบบจะเปลี่ยน PR เป็น **เสร็จสมบูรณ์** และปิดยอดสินค้าค้างรับทั้งหมด โดยคงยอดรับจริง เลขเอกสารเดิม และประวัติไว้ ไม่ต้องรับสินค้าให้ครบหรือกรอกเลขเอกสารก่อนปิดงาน การปิดงานครอบคลุม PO ทุกใบของ PR นั้น และบันทึกผู้ดำเนินการกับเวลาลงใน Timeline การกดซ้ำหรือข้อมูลที่เปลี่ยนระหว่างเปิดหน้าจะไม่ปิดยอดซ้ำ

ส่วนนี้ใช้โครงสร้างฐานข้อมูลเดิม ไม่เพิ่ม migration ทดสอบขั้นตอนด้วย `npm run test:e2e -- purchase-request-closure.spec.ts` บนฐานข้อมูลทดสอบเท่านั้น
